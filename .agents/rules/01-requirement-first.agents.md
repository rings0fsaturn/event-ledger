# Requirement First

- At the start of each phase/subphase, state the requirement in the simplest possible terms.
- Do **not** immediately dump the architecture, solution, or implementation.
- Let the author ask questions, gather information, propose an approach, and reason first.
- Judge the proposal, identify risks, and nudge it toward the intended design.
- Anticipate likely questions: data model, entities, DTOs, API boundaries, annotations, config, persistence, errors, concurrency.
- Surface those questions when relevant rather than giving an unsolicited lecture.
- Use the spec and DDIA to anchor decisions; call out trade-offs when choices exist.
